# dop-app — the DOP platform's cockpit

The DOP platform's web cockpit: the attention box, the tree of workspaces and
projects, and the demand's cockpit. It talks to the **BFF (`dop-api`)**; it has
no database and no business rule of its own.

**Before changing anything, read [`RAILS.md`](RAILS.md)** — it says what must
stay true after a change, and which decisions belong to the three repositories
that are not visible from here (the core, the BFF and the infrastructure). This
file says how to run the project; that one says how not to break it.

## Run & Operate

- `pnpm --filter @workspace/dop run dev` — the cockpit (it needs `PORT` and `BASE_PATH`; see `artifacts/dop/.env.example`)
- `pnpm run typecheck` — typecheck every package
- `pnpm run build` — typecheck + build
- `pnpm --filter @workspace/api-spec run fetch-spec` — downloads the BFF's spec into `lib/api-spec/openapi.json`
- `pnpm --filter @workspace/api-spec run codegen` — regenerates the hooks (react-query) and the schemas (zod) from the versioned spec
- `pnpm --filter @workspace/api-server run dev` — the local Express server (only the terminal's websocket; see "Architecture")

To see the cockpit with real data the BFF has to be up:

```bash
cd ../dop-api
CORE_GRPC=127.0.0.1:9226 FIREBASE_AUTH_EMULATOR_HOST=auth.localtest.me:8080 \
  uv run uvicorn app.main:app --port 8000
```

The attention box only fills up if the core's **worker** is running: it is what
consumes the events and builds the projection. With no worker, the API answers
`200` with an empty box — which looks like "nothing pending" and is not.

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9, React 19 + Vite
- Data: react-query with hooks generated by **Orval** from the BFF's OpenAPI
- Identity: **Firebase Auth** (the emulator in the local environment)
- Validation: Zod (`zod/v4`)

|---|---|

| The generated client (hooks) | `lib/api-client-react/src/generated/` |

| The old screens, on MOCK data | `artifacts/dop/src/pages/{home,workspace-*}.tsx` (the `/workspaces/*` routes) |

## Architecture decisions

- **The spec is versioned, not fetched during generation.** `fetch-spec`
  downloads it; `codegen` reads the file from the repository. Generation does not
  depend on a server being up, and every contract change shows in the review's
  diff.
- **No rule of the backend is reproduced in the front end.** The attention box's
  order, the badge, the items' priority and the demand's effective flow arrive
  ready from the API and are rendered as they arrived. A duplicated ruler is a
  ruler that diverges.
- **The active account is a per-request header** (`x-account-id`), read from an
  observable store on every call. Switching accounts clears react-query's cache:
  the generated keys do not include the account.
- **The `api-server` (Express) no longer serves an API.** After the BFF arrived,
  what was left in it is the local terminal's websocket (`/api/terminal`) and a
  process probe. See the integration slice's report for the recommendation.

## Gotchas

- `EventSource` cannot send a header, and the BFF requires `Authorization` and
  `x-account-id` in a header — so `GET /api/v1/stream/attention` is read by a
  `fetch` reader (`src/hooks/use-attention-stream.ts`), which sends the headers
  and resumes from the `id:` the server emitted. When the stream does not come
  up, the box keeps itself honest by rereading the REST endpoint, and the
  indicator on the screen says which of the two modes is in force.
- The Firebase emulator issues an `alg: none` token, **with no signature**. In
  production the signature really is verified. Nothing in the cockpit may depend
  on that difference.
- `vite.config.ts` requires `PORT` and `BASE_PATH` in the environment — without
  them the build fails at start-up, not later.
- `pnpm install` may fail compiling `node-pty` (an `api-server` dependency) on
  machines with no `node-gyp`. `pnpm install --ignore-scripts` solves it for
  whoever is only going to touch the cockpit.
